# 并发控制与重试优化文档

## 📋 概述

本文档详细分析 Docker 镜像同步平台的并发控制和重试机制的现状，并提供优化建议。

## 🔍 当前状况分析

### 📊 并发控制现状

| 功能模块 | 实现状态 | 描述 |
|---------|---------|------|
| **模拟批量同步** | ✅ 已实现 | 使用信号量控制 goroutine 并发数 |
| **真实批量同步** | ❌ 无并发控制 | 所有镜像一次性写入，无并发处理 |
| **任务级并发** | ❌ 无管理 | 多个用户任务串行处理 |
| **数据库操作** | ✅ 已优化 | GORM 内置连接池处理 |

### 🔄 重试机制现状

| 重试类型 | 实现状态 | 描述 |
|---------|---------|------|
| **Git推送重试** | ✅ 已实现 | `git_optimized.go` 中有推送重试逻辑 |
| **任务级重试** | ❌ 无实现 | 批量同步失败后需手动重试 |
| **镜像重试** | ❌ 无实现 | 失败镜像无法自动重试 |
| **手动重试** | ✅ 已实现 | 提供 `/api/v1/images/:id/retry` 接口 |

## 🎯 核心问题识别

### 1. 并发控制问题

#### 问题表现
- 多用户同时提交批量同步任务时系统响应变慢
- 没有全局并发限制，可能导致 GitHub API 限流
- 资源利用率不均衡

#### 代码证据
```go

```

#### 影响范围
- 系统吞吐量受限
- 用户体验不一致
- 资源浪费

### 2. 重试机制问题

#### 问题表现
- 批量同步失败后需要人工干预
- 配置的重试参数未被使用
- 错误恢复能力差

#### 代码证据

#### 影响范围
- 系统可靠性降低
- 运维成本增加
- 用户体验差

## 🚀 优化方案

### 🔥 1. 任务级并发控制（高优先级）

#### 设计目标
- 限制同时进行的批量同步任务数量
- 提高系统稳定性
- 防止 GitHub API 限流

#### 实现方案

```go
// 任务管理器
type TaskManager struct {
    maxConcurrent   int
    taskSemaphore   chan struct{}
    activeTasks     map[string]bool
    mutex          sync.RWMutex
}

func NewTaskManager(maxConcurrent int) *TaskManager {
    return &TaskManager{
        maxConcurrent: maxConcurrent,
        taskSemaphore: make(chan struct{}, maxConcurrent),
        activeTasks:   make(map[string]bool),
    }
}

func (tm *TaskManager) SubmitTask(taskID string, taskFunc func() error) error {
    // 获取信号量
    tm.taskSemaphore <- struct{}{}
    defer func() { <-tm.taskSemaphore }()

    tm.mutex.Lock()
    tm.activeTasks[taskID] = true
    tm.mutex.Unlock()

    defer func() {
        tm.mutex.Lock()
        delete(tm.activeTasks, taskID)
        tm.mutex.Unlock()
    }()

    return taskFunc()
}

// 在 SyncHandler 中使用
func (h *SyncHandler) SubmitBatchSync(c *gin.Context) {
    // ... 参数验证 ...

    taskID := uuid.New().String()

    // 使用任务管理器控制并发
    err := h.taskManager.SubmitTask(taskID, func() error {
        return h.processBatchSyncTask(req, taskID)
    })

    if err != nil {
        // 处理错误
    }
}
```

### 🔄 2. 智能重试机制（中优先级）

#### 设计目标
- 自动重试失败的任务
- 指数退避重试策略
- 尊量重试风暴

#### 实现方案

```go
// 重试管理器
type RetryManager struct {
    maxRetries    int
    baseDelay     time.Duration
    maxDelay     time.Duration
    activeRetries map[string]int
    mutex        sync.RWMutex
}

func NewRetryManager(maxRetries int) *RetryManager {
    return &RetryManager{
        maxRetries:    maxRetries,
        baseDelay:     time.Second,
        maxDelay:     time.Minute * 5,
        activeRetries: make(map[string]int),
    }
}

func (rm *RetryManager) ExecuteWithRetry(taskID string, taskFunc func() error) error {
    rm.mutex.Lock()
    rm.activeRetries[taskID] = 0
    rm.mutex.Unlock()

    for attempt := 0; attempt <= rm.maxRetries; attempt++ {
        err := taskFunc()
        if err == nil {
            // 成功，清除重试计数
            rm.mutex.Lock()
            delete(rm.activeRetries, taskID)
            rm.mutex.Unlock()
            return nil
        }

        // 更新重试计数
        rm.mutex.Lock()
        rm.activeRetries[taskID] = attempt
        rm.mutex.Unlock()

        // 指数退避延迟
        delay := time.Duration(math.Min(
            float64(rm.baseDelay)*math.Pow(2, float64(attempt)),
            float64(rm.maxDelay),
        ) * time.Second)

        logger.Logger.Warn("任务失败，准备重试",
            zap.String("task_id", taskID),
            zap.Int("attempt", attempt),
            zap.Int("max_retries", rm.maxRetries),
            zap.Duration("delay", delay),
            zap.Error(err))

        time.Sleep(delay)
    }

    return fmt.Errorf("任务失败，已重试%d次", rm.maxRetries)
}
```

### ⚡ 3. GitHub Actions 监控优化（中优先级）

#### 设计目标
- 减少 GitHub API 调用频率
- 避免 API 限流
- 提高监控效率

#### 实现方案

```go
// 批量监控服务
type GitHubMonitor struct {
    maxConcurrent   int
    monitorSemaphore chan struct{}
    cache          *StatusCache
    apiService      *GitHubAPIService
}

type StatusCache struct {
    statuses map[string]*CachedStatus
    mutex    sync.RWMutex
    ttl      time.Duration
}

type CachedStatus struct {
    Status      string
    LastUpdate  time.Time
    TTL         time.Duration
}

func (gm *GitHubMonitor) BatchGetStatus(runIDs []string) (map[string]string, error) {
    // 获取信号量
    gm.monitorSemaphore <- struct{}{}
    defer func() { <-gm.monitorSemaphore }()

    // 批量调用 GitHub API
    results := make(map[string]string)
    for _, runID := range runIDs {
        // 检查缓存
        status, cached := gm.cache.Get(runID)
        if cached {
            results[runID] = status
            continue
        }

        // 调用 GitHub API
        status, err := gm.apiService.GetWorkflowRunStatus(runID)
        if err != nil {
            logger.Logger.Error("获取GitHub Actions状态失败",
                zap.String("run_id", runID),
                zap.Error(err))
            continue
        }

        results[runID] = status
        gm.cache.Set(runID, status)
    }

    return results, nil
}
```

### 🎛 4. 任务队列管理（低优先级）

#### 设计目标
- 任务优先级管理
- 任务调度优化
- 负载均衡

#### 实现方案

```go
// 任务队列
type TaskQueue struct {
    highPriority chan *BatchSyncTask
    normalPriority chan *BatchSyncTask
    lowPriority  chan *BatchSyncQueue
    workers       []*Worker
    workerPool    *WorkerPool
}

type BatchSyncTask struct {
    TaskID       string
    Request      *models.BatchSyncRequest
    Priority     int
    CreatedAt    time.Time
    RetryCount   int
    MaxRetries   int
}

func (tq *TaskQueue) Enqueue(task *BatchSyncTask) {
    switch task.Priority {
    case 1:
        tq.highPriority <- task
    case 0:
        tq.normalPriority <- task
    default:
        tq.lowPriority <- task
    }
}

func (tq *TaskQueue) Dequeue() *BatchSyncTask {
    select {
    case task := <-tq.highPriority:
        return task
    case task := <-tq.normalPriority:
        return task
    case task := <-tq.lowPriority:
        return task
    }
}
```

## 🚨 风险评估

### 潜在风险

1. **并发控制风险**
   - 过低的并发数可能影响用户体验
   - 过高的并发数可能导致系统过载
   - 配置不当可能导致性能下降

2. **重试风险**
   - 无限重试可能导致资源浪费
   - 重试延迟设置不当可能延长故障时间
   - 重试风暴可能影响系统稳定性

3. **缓存风险**
   - 缓存失效可能导致性能下降
   - 缓存一致性错误可能导致数据不准确
   - 过期策略设置不当可能影响数据新鲜度

### 风险缓解措施

1. **配置限制**
   - 设置合理的并发数范围（1-10）
   - 设置最大重试次数限制（1-5）
   - 设置合理的延迟范围（1s-60s）

2. **监控告警**
   - 实时监控系统性能指标
   - 设置阈值告警机制
   - 建立故障响应流程

3. **优雅降级**
   - 高负载时自动降低并发数
   - API限流时使用缓存数据
   - 系统异常时提供基础功能
